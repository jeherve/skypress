# 0026 — Move to React 19 and the current `@wordpress` major line

- **Status:** Accepted (validated: full test suite, `astro check`, production build, and a
  browser smoke pass of the editor and reader islands)
- **Date:** 2026-10-21
- **Scope:** `react` / `react-dom` / their types, every direct `@wordpress/*` dependency,
  and the Node engine floor. **Supersedes the React 18 lock in Decision 0001** (the
  "React 18 is non-negotiable" premise). The rest of 0001 — Astro, islands, the
  `client:only` editor, light reading pages — is unchanged. Also retires the
  "keep `react` pinned at `18.3.1`" consequence in Decision 0021.

## Context

Decision 0001 locked SkyPress to React 18 for one reason: `@automattic/isolated-block-editor`
pulled React in through `@wordpress/element@6.24.0`, which required `react@^18.3`. The
host app has to share a single React instance with the editor, so the whole app stayed on
18.

Decision 0021 removed isolated-block-editor and made SkyPress depend on the
`@wordpress/*` packages directly. At that point `@wordpress/block-editor@15.x` still
declared `react: ^18.0.0`, so the lock stayed.

`@wordpress/block-editor@16.0.0` (July 2026) widened its peer range to
`react: ^18 || ^19`, and every `@wordpress` package SkyPress depends on did the same on
its next major. As of 2026-10-21 the current line (`block-editor@19.0.0`,
`components@43.0.0`, `element@10.0.0`, …) accepts either React. A tree-wide scan of
`node_modules` found nothing else that requires React 18: `@astrojs/react@5.0.7` accepts
`^17 || ^18 || ^19`, and the only remaining `react@^18` dependent was `react-dom@18`
itself.

## Options

- **A. Bump `@wordpress` to the current line, stay on React 18.** Works: the new peer
  range still includes 18. But it keeps a pin whose only justification is gone, and
  leaves SkyPress on a React line upstream is moving away from.
- **B. Bump `@wordpress` and move to React 19 together.** ✅ **Chosen.** Nothing in the
  tree holds us on 18 anymore, and both moves are verified by the same test/build/smoke
  pass.

## Decision

- `react` / `react-dom` → `19.3.1`; `@types/react` / `@types/react-dom` → `19.3.0`. The
  `overrides` entry for `react` / `react-dom` stays, now at `19.3.1`, so a stray
  transitive range can't pull a second copy of React into the island.
- Every direct `@wordpress/*` dependency → its current major (`block-editor@19.0.0`,
  `blocks@17.0.0`, `block-library@12.0.0`, `components@43.0.0`, `data@11.0.0`,
  `element@10.0.0`, …). Still no `@wordpress` overrides map (Decision 0021).
- `engines.node` → `>=22.13.0`, matching the floor the new `@wordpress` majors declare.

The only application code change is type-level: two form `onSubmit` handlers now type
their event as `SubmitEvent` instead of `FormEvent`, which the React 19 types deprecate.
The codebase uses none of the APIs React 19 removed (`ReactDOM.render`, `findDOMNode`,
string refs, function-component `defaultProps` / `propTypes`).

## Verification

- `npm test` (713 tests), `npm run check` (0 errors), `npm run build` all pass.
- `npm ls react react-dom` shows a single `19.3.1` copy; `npm ls` reports no invalid
  peers; each `@wordpress` store package (`data`, `core-data`, `notices`, `date`,
  `element`, `blocks`, `block-editor`) is installed exactly once.
- Browser smoke pass on `/write`: typing, `/` slash inserter, the block inserter
  popover, nested blocks (Quote), a link via ⌘K, the block settings sidebar, undo, the
  Publish → sign-in panel, and restoring a stored draft (heading, quote with a link,
  list) through the editor remount. On an article page, the `RecordJsonViewer` modal
  opens. No console errors.

## Consequences

- **React is no longer a constraint on `@wordpress` upgrades.** Bump the `@wordpress`
  packages together to their current line, dedupe, run the suite. The `resolve.dedupe`
  backstop in `astro.config.mjs` / `vitest.config.ts` stays.
- **Watch for a future `@wordpress` major that drops React 18** — irrelevant now, but it
  means we can't go back to 18 without also pinning `@wordpress` back.
- **Node 22.13+ is required** to install and build.
- A `memo: The first argument must be a component` warning appears in the block render
  tests: it comes from a circular import inside `@wordpress/block-editor`
  (`memo( BlockList )` runs before `BlockList` is defined when the package loads under
  vitest). It predates this change — trunk on React 18 / `block-editor@15.21.1` prints
  it too — and doesn't occur in the browser editor.
